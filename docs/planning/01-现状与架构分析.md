# 谛听安卓端功能扩展规划 · 01 现状与架构分析

> 本文档是「谛听安卓端功能扩展规划」系列的第一篇，用于给后续的功能清单与路线图提供事实基线。
> 分析对象：`android/app`（Flutter）、`rust/`（Rust 内核）、`shared/`（两端共用 UI 与配置读取）、
> `desktop/`（桌面端，作为“能力差集”与内核复用来源）。所有结论以仓库当前代码与 `Cargo.toml` 依赖为准。

---

## 1. 产品定位与设计原则

谛听（DITING）是 **本地优先的开源 DNS 加速与广告 / 追踪拦截工具**，GPL-3.0 授权：

- **本地优先**：上游解析加速、规则过滤、缓存与流量统计均在设备本地完成；除用户主动配置的远程订阅、
  更新检查与可选 LLM 助手外，不上传查询数据。
- **三端复用**：Android / Windows / Linux 共享一套 Rust 内核与 SQLite 数据格式，Android 与桌面端共享
  `shared/` 的设计系统、主题、l10n 与配置读取。
- **双原生库交付**：安卓随包交付 `libditing_engine.so`（隧道数据面 + DNS 管线）与
  `libditing_kernels.so`（合并的 UI 侧内核）。
- **工程规范**（`AGENTS.md`）：单代码文件 ≤ 600 行；任务完成自动提交；按变更风险决定测试范围。

## 2. 安卓端分层架构

```
android/app/lib
├── app/            # 应用入口、首启协议、升级重置、调试探针（app.dart / main.dart）
├── data/           # 数据层：db（sqflite 仓储）、native（Kotlin 通道）、agent、backup、
│                   #   rules、subscriptions、vpn、server、prefs、tools、update、cleanup、export
├── state/          # Riverpod 状态：work_mode、power、rules、subscription、observability、
│                   #   dashboard、on_demand、diagnostics、auto_update、agent 等
├── pages/          # 页面：home(dashboard) / hub(功能中心) / logs / traffic / tools /
│                   #   rules / subscriptions / server / settings / config / system / mode / about
├── routes/         # go_router 子路由按域拆分（hub_routes、logs_routes、system_routes…）
├── shell/          # 底部导航外壳
├── overlay/        # 悬浮日志窗
└── widgets/        # 通用组件
android/app/android/app/src/main/kotlin/com/haoze/diting
├── normal/ express/ server/   # 三模式的 VpnService 与配置
├── engine/                    # Rust 引擎加载与 JNI 桥
├── core/rule/                 # 规则索引编译 / snapshot 存取（读 .dtri、组装 snapshot）
├── log/                       # DNS / 请求 / 流量 / 运行事件 / 崩溃日志写入
├── net/                       # Ping / Trace / DNS / 网卡探测
├── proxy/                     # 出站代理桥
├── watchdog/                  # 隧道看门狗与回收
├── widget/ tile/              # 桌面小组件、快捷设置磁贴
├── platform/                  # 通知、权限、后台、更新、SSID 读取等平台桥
└── QuickActionActivity        # 自动化广播入口（START/STOP/TOGGLE）
```

**关键机制**：

- UI 侧内核（规则解析、订阅、备份、日志查询、DNS 配置文档等）**只有 Rust 一份实现**：Dart 通过
  `dart:ffi` 调用 `libditing_kernels.so`，缺失即报错，不做第二套 Dart 降级实现。
- 隧道数据面（socket、TUN、DNS 管线、MITM）在 `libditing_engine.so`，由 Kotlin `VpnService` 经 JNI 驱动。
- 一切对外配置（DNS 配置、规则快照、TUN 路由计划、代理配置）都经 `diting-*-config-core` 归一化，
  保证“App 拼写的字符串”与“引擎读取的字符串”不可能不一致。

## 3. Rust 内核全景

工作区共 49 个 crate。按归属分为三组（以 `diting-engine/Cargo.toml` 与 `diting-kernels/Cargo.toml`
的直接依赖为准）：

### 3.1 隧道引擎内核（链接进 `libditing_engine.so`）

| crate | 职责 |
|---|---|
| diting-engine | 引擎主体：生命周期、DNS 管线、三模式、TUN/smoltcp 数据面、JNI 门面 |
| diting-config-core | DNS 配置 / 协议名 / 块响应 / DoQ / rewrite 表的归一化与校验（含错误文案） |
| diting-dns-core | DNS 报文解析、空块判定、动态阻断升级、合成应答（阻断/改写/本地资产/DDR） |
| diting-dns-cache-core | 64 分片并发 LRU 缓存、TTL 三档策略、后台清扫、快照投影 |
| diting-dns-wire | 缓存与 DNS 内核共享的线格式层（缓存键、名字解码、记录遍历、TTL 补丁） |
| diting-go-compat | Go `regexp` / `strings` 语义兼容，供规则与策略内核复用 |
| diting-policy-core | 规则表、通配符索引、`.dtri` 订阅 trie、七级优先判定、决策缓存 |
| diting-resolver-core | 上游服务商统计（SRTT/EWMA/连败惩罚）与四策略调度计划 |
| diting-upstream-core | 四种上游传输常量、分帧、DoH 状态分类、DoT 空闲池、模式分派表 |
| diting-bootstrap-core | 加密上游域名的 bootstrap 打分、加权选择、冷却与 host 缓存 |
| diting-telemetry-core | 日志批队列、按 UID 流量计数、UID / 包名 TTL 缓存 |
| diting-gate-core | 准入顺序（连接门） |
| diting-connlog-core | 连接日志去重 |
| diting-proxy-core | SOCKS5 / HTTP CONNECT 编解码与代理配置归一化 |
| diting-cert-core | MITM 根 CA 生命周期、叶证书签发、EV 策略 |
| diting-mitm-core | MITM “智能过滤”策略（UID 允许、旁路、黑名单） |
| diting-cosmetic-core | Cosmetic 元素隐藏的流式注入与本地样式资产服务 |
| diting-sniffer-core | TLS ClientHello SNI / 明文 HTTP Host 嗅探分类 |
| diting-request-core | URL 前缀请求规则（block / allow）与匹配 |
| diting-ipcache-core | IP→域名 LRU（直连 IP 流仍能贴域名标签） |
| diting-allowlist-core | 应用白名单授权（按 UID 的域名集 / IP 授权 / TTL 过期） |

> 注：`diting-ipcache-core`、`diting-allowlist-core` 的文档注释标注为“安卓隧道引擎”内核，
> 但当前 `diting-engine/Cargo.toml` 未直接列出，可能经其它路径复用或为历史保留，落地时需核对。

### 3.3 桌面端专用内核（Go 服务经 `purego` 运行期 dlopen，安卓未链接）

| crate | 职责 | 对安卓的可复用性 |
|---|---|---|
| diting-stamp-core | `sdns://` DNS stamp 解析 | 中：自定义 provider 导入 |
| diting-filter-core | 桌面过滤引擎的规则索引与匹配（反向标签 trie、bloom、`$denyallow`/`$to`） | 高：与 policy-core 同源思路 |
| diting-rewrite-core | 桌面 `$dnsrewrite` 记录构造与重写引擎 | 中：安卓已有 rewrite 表 |
| diting-safebrowsing-core | Safe Browsing / 家长控制 哈希前缀查询与缓存 | **高：安卓可直接接入** |
| diting-hosts-core | 本地 hosts 文件权威解析（A/AAAA/PTR） | 中：自定义 hosts |
| diting-dns64-core | RFC 6052/6147 DNS64 合成 | **高：IPv6-only 网络** |
| diting-ratelimit-core | 每客户端令牌桶限速与 CIDR 豁免 | 中：服务器模式 LAN 客户端 |

> `diting-netstack-spike`、`diting-mitm-spike`、`diting-tun-spike` 为迁移期 Stage 0 验证 crate，
> 不进产物；`diting-corpus` 为行为冻结回归语料。

**战略含义**：`safebrowsing`、`dns64`、`ratelimit`、`filter`、`rewrite` 这 5 个内核在桌面端已成熟，
**安卓端尚未链接**。把其中与 DNS 管线同构的（safebrowsing / dns64 / filtered 规则增强）接入安卓引擎，
是成本最低、收益最高的“内核杠杆”路线。

## 5. 桌面端 ↔ 安卓端能力差集（Feature Parity 机会）

桌面端已实现、安卓端缺失、且**能直接复用现有 Rust 内核或同构代码**的能力，是本次扩展的“低垂果实”：

1. **规则测试器 / 模拟器**（`/filter/check`）→ 安卓引擎已持有 `policy-core::Snapshot`，加一个
   “只判定不转发”的 FFI 即可，复现“命中规则 / 来源列表 / 原因 / rewrite”。
2. **分时拦截 / 时间计划**（filter schedule）→ 复用 `diting-subscription-core::schedule` 的
   时间槽算法，新增自动化调度内核，驱动引擎开关。
3. **临时暂停拦截**（到期自动恢复）→ 复用计时/调度逻辑。
4. **隐私套件**：
   - Safe Browsing / 家长控制 → 直接接入 `diting-safebrowsing-core`；
   - Safe Search 强制 → 新增 rewrite 规则生成（复用 `rewrite-core` 思路）；
   - ECS 策略 / 记录类型阻断 / 重绑定防护 → DNS 管线开关，改 `dns-core` + config 文档；
   - blocked services 预设分组 → 规则模板（复用 `rule-core` 导入）。
5. **DNS64** → 直接接入 `diting-dns64-core`（IPv6-only 蜂窝/Wi-Fi 场景）。
6. **缓存预取 / 持久化 / 排除** → `dns-cache-core` 已有快照与策略，补 UI 与持久化。
7. **客户端分组 / 每客户端限速**（服务器模式）→ 接入 `diting-ratelimit-core`，增加 LAN 客户端视图。

## 6. 架构约束与扩展原则

后续所有新功能必须遵守这些约束（会影响路线图与工作量评估）：

1. **内核唯一实现**：任何判定逻辑落在 Rust，Dart/Kotlin 不写第二套语义；缺失库即报错，不静默降级。
2. **配置归一集中**：新增配置项须进 `diting-*-config-core` 的文档构建与校验，避免字符串漂移。
3. **FFI 边界**：安卓 UI 内核用 C ABI（`dart:ffi`）；隧道数据面用 JNI。新增内核按调用方选择其一，
   并维护 `ABI_VERSION`。
4. **单文件 ≤ 600 行**：新页面按 `pages/<域>/` 拆分 `part`，新内核按模块拆分。
5. **时间注入**：所有含时间的判定（调度、缓存过期、限速、冷却）必须接受注入时钟，便于单测重放。
6. **GPL-3.0 传染性**：借鉴开源实现只能借鉴“设计与机制”，不得直接拷贝不兼容许可证（Apache-2.0 / MIT
   与 GPL-3.0 兼容可借鉴代码思路；MPL-2.0 需注意文件级隔离）。详见各调研稿的许可证提示。
7. **体积与性能**：包体已做 ~12% 收缩；新增内核优先复用现有依赖（`quinn`、`rustls`、`smoltcp`），
   避免引入重依赖。
