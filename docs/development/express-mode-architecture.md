# DITING 极速模式架构设计与技术规范

> 状态：已落地验证 | 创建：2026-10-05 | 适用版本：DITING v1.0.0+

本文档详细记录 DITING 极速模式（Express Mode）的架构设计、数据面实现、DNS 劫持路由机制、独立视图层设计以及功能取舍考量。

---

## 1. 背景与模式定位

DITING 支持三种独立工作模式：

| 模式 | 系统门槛 | 核心技术栈 | 定位与核心能力 |
|---|---|---|---|
| **极速模式 (Express Mode)** | **Android 7.0+ (API 24)**<br>`arm64-v8a` | **纯 Kotlin 原生实现**<br>轻量窄路由 TUN + Kotlin DNS 引擎 | 轻量、极低功耗。聚焦核心 DNS 加速、规则过滤（订阅+黑白名单）、多档缓存与日志。去除 Go 内核依赖，下潜至 Android 7 老旧设备。 |
| **普通模式 (Normal Mode)** | **Android 10.0+ (API 29)**<br>`arm64-v8a` | **Go 用户态网络栈**<br>(gVisor netstack + AAR) | 全功能网络管控。支持全隧道接管、HTTPS 流量解密检查、应用级联网管控、出站代理与实时流量统计。 |
| **服务器模式 (Server Mode)** | **Android 10.0+ (API 29)**<br>`arm64-v8a` | **Go 独立 DNS 服务**<br>(监听 `0.0.0.0:1053`) | 局域网独立 DNS 服务器，供外部路由器、PC 与移动设备将 DNS 指向本机解析。 |

极速模式的核心定位为**「普通模式核心 DNS 能力的原生轻量 Kotlin 实现」**，旨在保持核心网络交互体验和 DNS 规则治理能力的前提下，摆脱大体积与高资源消耗的用户态全网络栈，让老旧设备和注重续航的用户获得极致流畅的体验。

---

## 2. 核心架构设计理念：物理隔离与复制复用

为确保普通模式既有稳定性与极速模式演进自由度，极速模式遵循以下核心工程原则：

1. **新文件优先，集中于独立模块**：
   - 极速模式所有核心逻辑、数据面、传输层、服务与独立 UI 均位于 `com.haoze.diting.express` 包下。
   - 旧业务代码（如 `DnsVpnService.kt`、`MainScreenContent.kt`、`FeatureHubScreen.kt`）保持 **零污染、零侵入**，坚决避免为了所谓的“代码复用”在旧文件中增加模式分支与动态门控。
2. **复制复用优先（Source-level Clone & Adapt）**：
   - 对于可复用的成熟逻辑（DoH 通信客户端、DNS 报文编解码与 TTL patch、前台通知构建、UI 布局结构等），采用源码级复制至 `express/` 包下独立演进与适配。
   - 彻底切断底层运行时耦合，杜绝修改一处导致另一模式产生连带 Bug 的风险。
3. **最外层极简委托**：
   - 宿主 Activity（`MainActivity`、`LogRouteActivity`、`SettingsRouteActivity`）仅在最外层依据 `AppWorkMode.EXPRESS` 进行极简单行委托分流。

## 3. 数据面架构：DNS 专用 VPN（窄路由）

普通模式采用全网络路由与 Go 用户态网络栈，而极速模式采用 **DNS 专用窄路由 TUN**：

### 3.1 TUN 地址与窄路由配置
- **虚拟 IPv4**：`10.0.0.2/30`，网关与虚拟 DNS 地址为 `10.0.0.1`。
- **虚拟 IPv6**：`fd00:abcd::2/64`，网关与虚拟 DNS 地址为 `fd00:abcd::1`。
- **路由表注入**：
  - 仅添加 `10.0.0.0/30` 和 `fd00:abcd::1/128`。
  - 注入预设的公共 DNS 劫持 IP 清单（`/32` 与 `/128`）。
  - **绝不添加默认路由 `0.0.0.0/0` 或 `::/0`**。
- **流量路径**：
  - 只有发往虚拟 DNS 或劫持公共 DNS IP 的流量进入 TUN。
  - 设备的所有常规应用数据（TCP/UDP/QUIC）直接通过底层物理网络传输，完全不经过 VPN 协议栈，天然实现零性能损耗与零额外电量消耗。

### 3.2 报文编解码与快速拒绝（ExpressPacketCodec）
- **IPv4 / IPv6 解析**：校验版本、IHL、总长，智能跳过 IPv6 逐跳与路由扩展头；非首片 IP 分片主动丢弃。
- **UDP:53 查询**：直通 `ExpressDnsEngine` 处理并构建校验和正确的应答包写回 TUN。
- **非 53 端口 TCP RST 快速拒绝**：
  - 当外部连接误向被劫持的公共 DNS IP 发送非 53 端口流量（如发往 `8.8.8.8:443` 或 `8.8.8.8:853`）时，`ExpressPacketCodec` 立即构造 TCP RST 响应写回 TUN。
  - 该机制避免客户端连接挂死并等待数十秒超时，保障网络平滑降级。
- **内存复用机制**：读循环维护单线程固定缓冲区，避免逐包内存分配放大，大幅降低老旧设备的 GC 压力。

## 4. 公共 DNS 劫持清单维护

硬编码公共 DNS（如 8.8.8.8）的应用若未被 TUN 捕获，可能会绕过本地过滤。因此极速模式首版内置公共 DNS 劫持机制：

- **IPv4 劫持列表**（约 20 个主流公共节点）：
  - Google DNS：`8.8.8.8`, `8.8.4.4`
  - Cloudflare：`1.1.1.1`, `1.0.0.1`
  - Quad9：`9.9.9.9`, `149.112.112.112`
  - OpenDNS：`208.67.222.222`, `208.67.220.220`
  - 阿里 DNS：`223.5.5.5`, `223.6.6.6`
  - 腾讯 DNSPod：`119.29.29.29`
  - 114 DNS：`114.114.114.114`, `114.114.115.115`
  - 百度 DNS：`180.76.76.76`
  - Yandex DNS：`77.88.8.8`, `77.88.8.1`
  - AdGuard DNS：`94.140.14.14`, `94.140.14.15`
  - CleanBrowsing：`185.228.168.9`, `185.228.169.9`
  - Neustar UltraDNS：`64.6.64.6`, `64.6.65.6`
- **IPv6 劫持列表**：
  - Google IPv6：`2001:4860:4860::8888`, `2001:4860:4860::8844`
  - Cloudflare IPv6：`2606:4700:4700::1111`, `2606:4700:4700::1001`

- **自适应路由注入**：
  - 仅在用户开启 IPv6 且底层网络具备有效 IPv6 连通性时才向 TUN 添加 IPv6 劫持路由，防止纯 IPv4 网络下因添加 IPv6 路由导致网络黑洞。

## 5. DNS 引擎与独立传输层

### 5.1 查询处理管线（对齐 Go 顺序）
1. **DDR 防绕过**：查询 `_dns.resolver.arpa` 强制返回 NXDOMAIN，阻止客户端自行协商加密 DNS。
2. **规则匹配判定**：委托 Room 规则库与内存索引判定黑白名单及订阅规则；命中时根据配置构造阻断应答（NXDOMAIN、REFUSED 或零地址）。
3. **Room 缓存查询**：查询本地持久化 DNS 缓存表，命中且未过期时直接写回。
4. **上游分发与并发竞速**：委托 `ExpressUpstreamDispatcher` 向目标 DNS 服务商分发请求。

### 5.2 上游调度策略（四种模式）
- **单一模式 (SINGLE)**：直接发送至用户选定的主 DNS 服务商。
- **并发竞速 (PARALLEL_RACE)**：同时向多个上游发起协程并发查询，首个有效响应获胜并写回，其余协程立即取消并主动关闭底层 Socket，释放 IO 线程。
- **依次重试 (PRIMARY_BACKUP)**：按顺序逐个尝试上游，超时或失败时无缝 failover。
- **智能预测 (SMART_PREDICTION)**：首版对齐竞速机制保障极速响应。

### 5.3 极简 DNS-over-TCP 终结器（ExpressTcpDnsHandler）
客户端在 UDP 响应被标记为 TC（截断）或特定环境下会尝试使用 TCP 53 端口查询。`ExpressTcpDnsHandler` 实现了超轻量的用户态 TCP 终结：
- 处理 SYN/ACK 三次握手并分配序号跟踪。
- 接收客户端带有 2 字节长度前缀的 DNS 报文载荷，交付 `ExpressDnsEngine` 解析。
- 将应答拼装为 TCP 数据段分帧写回，并在收到 FIN/RST 时安全清理连接。

## 6. 独立 UI 视图层与功能裁剪

### 6.1 物理隔离的专属 UI
- `ExpressMainScreen` 与 `ExpressHomeContent`：保留电源启停、DNS 服务商切换、解析模式选择卡片；移除了依赖全隧道的局域网绕过开关与实时网速卡片。
- `ExpressFeatureHubScreen`：基于网格布局紧凑排列，**物理移除 9 项不支持的高级功能**，不保留任何不可用入口或动态灰显门控。
- `ExpressNavigation`：定义极速模式专属底栏目的地（`HOME`、`FEATURE_HUB`、`LOG_DASHBOARD`、`SETTINGS`），自动过滤全隧道专属 Tab。
- `ExpressRequestLogScreen`：纯净 DNS 日志查看器，物理剔除 HTTPS 流量标签页与 AI 流量分析操作。

### 6.2 功能取舍矩阵

| 功能模块 | 普通模式 (Go 全隧道) | 极速模式 (Kotlin 原生) | 取舍说明 |
|---|---|---|---|
| 电源启停 / 服务商选择 | ✅ 支持 | ✅ 支持 | 完全对齐 |
| 四种解析调度模式 | ✅ 支持 | ✅ 支持 | 完全对齐 |
| 域名黑白名单 / 订阅规则 | ✅ 支持 | ✅ 支持 | 共享同一套 Room 规则库 |
| DNS 缓存与统计 | ✅ 支持 | ✅ 支持 | 共享持久化缓存数据库 |
| 悬浮日志 / 请求日志 | ✅ 支持 | ✅ 支持 | 仅呈现 DNS 请求流 |
| 覆写名单 (Rewrite List) | ✅ 支持 | ❌ 物理移除 | 依赖特定全隧道重定向能力 |
| 应用流量统计 / 状态栏网速 | ✅ 支持 | ❌ 物理移除 | 窄路由无普通应用流量经过 |
| 应用独立规则 / 禁止联网 | ✅ 支持 | ❌ 物理移除 | 依赖全隧道 IP 丢弃能力 |
| 排除应用 (Bypass) | ✅ 支持 | ❌ 物理移除 | 窄路由天然不接管普通应用 |
| HTTPS 流量检查 (CA 证书) | ✅ 支持 | ❌ 物理移除 | 依赖 TLS 中间人解密引擎 |
| 出站代理 (SOCKS5/HTTP) | ✅ 支持 | ❌ 物理移除 | 窄路由无通用出站流量 |
| 网络诊断 (Ping/测速) | ✅ 支持 | ❌ 物理移除 | 聚焦纯粹 DNS 加速定位 |
| AI 流量研判助手 | ✅ 支持 | ❌ 物理移除 | 极速模式保持轻量无冗余 |

## 7. 配置迁移与隔离保障（ExpressConfigAdapter）

为避免极速模式用户导出配置时混入不支持的脏配置，以及导入全量备份时污染本地存储：

- **导出纯净化**：`ExpressConfigAdapter.sanitizeExportSelection()` 强制关闭 9 项全隧道功能的导出开关。
- **导入无害化**：`ExpressConfigAdapter.sanitizeImportConfig()` 在解析导入文件时，物理剥离并清空出站代理、HTTPS 检查、应用放行黑白名单及流量统计配置，保障极速模式下的配置导入安全可靠。

## 8. 构建与验收规范

- **单文件行数红线**：所有新建 Kotlin 文件严格控制在 **600 行以内**，结构清晰，职责单一。
- **测试覆盖**：
  - 数据面编解码、IPv6 扩展头跳过、TCP RST 回写与分帧重传单元测试；
  - 上游传输协议、并发竞速协同与取消安全性测试；
  - 极速导航路由与配置适配器纯净化单元测试。
- **全量回归保障**：普通模式与服务器模式代码零侵入，全量测试套件持续全绿，确保高质量发布。
